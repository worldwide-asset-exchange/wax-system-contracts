# WAX Contract Audit Protocol (WCAP) — v1.1

A repeatable, evidence-driven security audit protocol for WAX Antelope/C++ contracts, written
so that a person or an agent can run it from a clone of this repository and produce the same
artefacts every time. This file is the protocol. The tooling it names lives under `.audit/`;
the findings it produces do not live in this repository (see [§2](#2-the-privatepublic-boundary)).

First application: `wax-system-contracts`, 2026-09. Revision history is at the end.

---

## 0. What an audit under WCAP produces

| Artefact | Where | Generated by |
|---|---|---|
| `scope.yaml` — commit, tag, file list, hashes, explicit out-of-scope list | private repo | Phase 0, by hand from measurements |
| `threat-model.md` — assets, actors, boundaries, invariants | private repo | Phase 1 |
| Static-sweep results, baseline and self-test | this repo, `.audit/rules/` | Phase 2, CI |
| `findings/<ID>.yaml` — one file per finding, schema in §6 | private repo | Phase 3–5 |
| Regression and invariant tests | this repo, `tests/` | Phase 4, 6 |
| Final Report (markdown source → Confluence page) | private repo `.audit/report-src/` → Confluence | Phase 5, `render.py` + `build-report.py` + `md2html.py` |
| Scorecard (markdown source → Confluence page) | same | Phase 5 |
| Report PDF | rendered from the findings JSON, attached to the report page and the ticket | `.audit/report/build-pdf.py` |
| Jira tickets, one per finding | `WBP` project | `render.py --jira` |

Every artefact is derived from the findings YAML or from a script over the source; nothing in
the register, the verification table, the coverage figures or the deployment tables is typed
by hand. The narrative sections of the report are prose and are edited as prose.

## 1. Prerequisites

- A clone of this repository (public) and of the private audit repository (findings, threat
  model, report sources). The private repository is a mirror of this one that carries the
  audit branch and its tags; the report tooling that reads findings lives only there.
- Docker, and the build image pinned in the `Makefile` (`waxteam/waxdev:<version>`). Every
  build and every test run happens inside it. On a shared host, cap the container
  (`--cgroup-parent`, `--cpus`) and run one build at a time.
- `python3` with `pyyaml` and `jinja2`; `google-chrome` for the PDF.
- Access to the tracker project (`WBP`) and to the audit's Confluence space for publishing.
- A public WAX API endpoint for on-chain checks (`get_code_hash`, `get_table_rows`,
  `get_account`); no key material is ever needed by the audit.

---

## 2. The private/public boundary

This is a hard rule, checked before every push.

**Never in a public branch:** `findings/`, `scope.yaml`, `threat-model.md`, leads and triage
notes, hand-off notes, live-chain snapshots taken for the audit, the report sources and the
rendered report or its JSON, and any test that asserts an unremediated defect. `.gitignore`
guards the file families; `git diff --cached --name-only` is still read before every push.

**Public, and meant to be:** the static rules and their baseline, the coverage measurement,
the hash-verification and reproduction scripts, the PDF template and non-sensitive metadata,
invariant and regression tests that assert *correct* behaviour, `SECURITY.md`, and this file.

**Timing:** a finding's fix lands in a public PR only after the finding is recorded; the
report and PDF stay private until every Critical/High/Medium is fixed *and deployed*, and are
released only on the owner's explicit decision. Security debt is referenced in public by
tracker ID only.

---

## 3. Provenance and sign-off

Every external-facing artefact carries this line verbatim:

> Security review performed internally using Claude (Anthropic) — Opus 5 for audit phases 0–5, Fable 5.1 for remediation and reporting.

It is an internal self-assessment, not a third-party attestation, and every artefact says so.
Scores are judgements: a score changes only with a stated basis in the scorecard's revision
history, and the report's owner signs off every published revision. A revision that quietly
changes a claim is worth less than one that records the correction (§9, Retractions).

## 4. The phases

Phase numbering is stable; each phase has an input, a command or method, an output and a pass
condition. Effort figures are deliberately absent: they belong to the plan, not the protocol.

### Phase 0 — Freeze & reproduce

- Pin the audit commit and tag it `audit/<yyyy-mm>/<scope>`. Every finding cites `file:line`
  at that tag.
- Build in the pinned image (`make build && make -C build`, inside the container) and record
  the SHA-256 of every contract WASM.
- Compare against the code hash live on mainnet: `.audit/verify-hashes.sh build`. For any
  account whose hash does not match current source, find which tag in which toolchain does:
  `.audit/reproduce-deployed.sh <ref> <image>`; the deployed ABI's `version` field narrows
  the compiler generation first.
- **Pass:** every deployed contract in scope is reproduced bit for bit from a named source
  and toolchain. A contract that cannot be reproduced is a finding on its own (class E4).
- **Output:** `scope.yaml`.

### Phase 1 — Threat model

Assets → actors → trust boundaries → invariants, written *before* any line-by-line review
(template: `.audit/templates/threat-model.md`). The invariants are what turn a code read into
a test; nothing in Phase 3 starts before they are written down. Measure, don't assume: any
chain fact the model relies on (producer count, authority layouts, live table contents) is
read from the chain and dated.

For a system contract the invariant set has been:

| | Invariant |
|---|---|
| I1 | Conservation — tokens issued per settlement equal the sum of every bucket and burn, with no unaccounted remainder |
| I2 | No double claim — every claim action is idempotent within its period and fails closed |
| I3 | Schedule determinism — identical chain state and identical deployed bytecode yield an identical producer schedule (the contract's hash is consensus-enforced; WASM `f64` is deterministic) |
| I4 | Solvency — no payout exceeds the balance or bucket that backs it |
| I5 | Authority monotonicity — no action lets a non-privileged actor gain authority over an account or the contract |
| I6 | Bounded cost — every action, and everything reachable from the block hook, terminates within a block's budget at realistic and at maximal table sizes |
| I7 | Upgrade integrity — the WASM on chain equals the hash of the audited commit built in the pinned image |

**Output:** `threat-model.md`. **Pass:** every invariant has a named owner test or a stated
reason it cannot be tested.

### Phase 2 — Automated sweep

- `python3 .audit/rules/wcap-check.py contracts --baseline .audit/rules/baseline.txt` — the
  type-aware checks (classes in §5), keyed `file|class|symbol` so the baseline survives
  line-number churn. `python3 .audit/rules/test_wcap_check.py` is its self-test.
- `.audit/rules/run-sweep.sh` adds the semgrep idiom rules.
- `python3 .audit/rules/test-coverage.py` — action-reference and guard-branch coverage
  (line/branch instrumentation is not possible in the contract toolchain; the guard figure is
  the honest number and is printed after every CI build).
- **Rules:** precision over coverage. A rule that cannot be made precise is a manual review
  item, not a rule. The baseline may only shrink; each removed line is either a fix or a rule
  made more precise, and the commit says which.
- **Pass:** zero untriaged hits; every baselined line carries a reason.

### Phase 3 — Manual review, delta-first

- Establish the upstream baseline by measurement (diff the tree against candidate upstream
  releases; the smallest diff is the baseline).
- Two depths: **full** on code the project added or heavily modified (every privileged setter
  read individually); **differential** on upstream-identical files (the diff plus its blast
  radius, deployed binaries reproduced). External contracts whose state enters a consensus
  path are read at full depth, at every commit that matters.
- Per file, walk the taxonomy (§5) and record a verdict for every class. "Not applicable" is a
  required answer: it is what makes coverage auditable.
- Standing review items: the error message must describe what the check enforces; compare
  siblings (`reg*`/`edit*`, paired setters, twin payout paths) and diff them, the weaker copy is
  usually the finding; read prose beside code (comments that contradict the line under them,
  commented-out checks); evaluate the degenerate input (empty, duplicate, maximal) of every
  privileged vector-taking action; and verify consensus arithmetic and node behaviour against
  the node source, not from memory.
- Two-reviewer rule on the highest-priority files: independent passes, then reconcile.
- **Output:** leads, then findings (§6). **Pass:** the file × class coverage matrix is
  complete.

### Phase 4 — Invariant & property testing

Turn I1–I7 into executable tests in the existing suite. Conservation is measured across a
settlement, not eyeballed; claims are replayed within a period; solvency is a property test;
cost is measured at the cap *and* at a full candidate set (an opt-in long case is fine, as
long as it is proven to time the block that does the work). Proof tests that assert current
behaviour while a fix is pending carry a documented inversion; the inversion becomes the
regression test. Close the coverage gaps Phase 2 listed.

**Pass:** every invariant green or its reason recorded; every finding has a reproduction.

### Phase 5 — Report & triage

- One `findings/<ID>.yaml` per finding (§6). `python3 .audit/render.py --summary` must exit
  0: it rejects a stated severity that contradicts impact × likelihood (§7).
- `render.py --jira` produces the ticket payloads; `render.py --report-data` the PDF JSON;
  `render.py --report-tables` the markdown tables the report includes (register, verification,
  counts). `build-report.py` expands the report source's include markers; `md2html.py` renders
  it for Confluence; `.audit/report/build-pdf.py` renders the PDF.
- Dismissed candidates are recorded with their reasoning in the report, so a reader can tell
  "examined" from "missed".
- Report section order: header (scope, deployed state, provenance) · scope and method · executive
  summary · the pattern · findings register · independent re-verification · invariants ·
  upstream differential · deployed-source provenance · external contracts · remediation and
  deployment · retractions and corrections · dismissed with reasoning · coverage · what to
  change in the protocol · recommended next steps.
- **Pass:** every finding has a ticket, a severity that matches the matrix, and a proof.

### Phase 6 — Remediate & re-verify

- Each finding → its own branch → fix plus a regression test that **fails on the pre-fix
  commit** at a recorded line and passes on the fix. Contract changes get two independent
  review passes. The baseline shrinks by the lines the fix clears.
- A session that did not write the fix re-runs the regression test against the pre-fix
  binary and the fixed binary, reads the fix for class-versus-symptom, and records the
  verdict, the red line and the date in the finding's `remediation.verified_by` /
  `verified_at` / `verification`. Where no runtime red is possible (a structural pin, a
  compile-time assert), the verdict says so rather than manufacturing one.
- `status` moves `open → fixed` only when the fix is merged; `remediation.deployed` is filled
  with the deploy transaction only when the code hash on chain matches the tag's build.
- **Pass:** no open Critical/High; every fixed finding independently verified.

### Phase 7 — Continuous

The sweep, the self-test, the coverage figure and the invariant suite run in CI on every PR
and gate the merge. Deploys are generated from live chain state and verified by hash after
execution. The hash comparison is re-run quarterly and on every deployment. Any PR touching a
file that carries an invariant reopens that invariant's review. Annual external audit scoped
to the delta, with the internal corpus handed over as input.

## 5. Taxonomy

Every class gets an explicit finding-or-not-applicable verdict per file. IDs are stable and
are what the static rules report.

**A. Authorization** — A1 missing `require_auth` on a state-mutating action (nodeos-native
actions in the system contracts, chain-only senders such as `onerror`, and empty receipt
emitters are classified, not baselined) · A2 `get_self()` where a named permission was
intended, and vice versa · A3 `eosio.code` assumptions for inline actions · A4 privileged-action
inventory: each enumerated, each reachable only through the intended multisig · A5
`eosio.wrap` / `eosio.msig` bypass paths.

**B. Notification & inline-action flow** — B1 `on_notify` without `get_first_receiver()` ·
B2 transfer handler without `to == get_self()` · B3 inline re-entrancy and recursion depth ·
B4 failure atomicity across inline sends.

**C. Arithmetic & representation** — C1 truncation and dust in splits · C2 overflow in `int64`
asset math and `uint64` accumulators, and narrowing into `uint32` · C3 asset symbol/precision
mismatch, negative or zero quantity, non-finite floating input · C4 floating point in a
consensus-ordering path, including sort comparators · C5 always-true comparisons on unsigned
types · C6 message/check mismatch (strict wording on a non-strict operator, a number in the
message that is not the number compared, siblings validating the same input differently).

**D. Resource & data-structure abuse** — D1 unbounded iteration in an action · D2 RAM-payer
griefing · D3 an assertion or throwing read reachable from the block hook (a failing block
hook does not halt the chain; it freezes everything the hook drives) · D4 secondary-index and
key assumptions that break at scale or collide.

**E. Upgrade & state migration** — E1 table layout change without binary extensions; a state
struct with a user-provided constructor and an uninitialised member · E2 singleton
default-construction after a struct change · E3 `setcode` process: quorum, verification, the
parameter raise an inline `exec` needs · E4 deployed WASM ≠ audited source.

**F. Cross-contract & oracle trust** — F1 another contract's table read as truth · F2 code-hash
allow-list checked on every read, and equal to exactly the live code · F3 fallback behaviour
when the external contract is absent, renamed or emptied (fails open? who can trigger it?) ·
F4 stale or missing oracle data.

**G. Economic & game-theoretic** — G1 conservation and rounding residue · G2 vote-weight growth
curves and precision ceilings · G3 standby-slot gaming and ban-list centralisation · G4
proxy/sybil economics and exclusion thresholds · G5 proposal griefing, reviewer collusion,
claim races · G6 market-parameter manipulation · G7 producer ordering around claims.

**H. Process & supply chain** — H1 toolchain pinning and provenance · H2 CI integrity · H3
disclosure policy · H4 key custody of the accounts that gate the above.

## 6. Finding schema (`findings/<ID>.yaml`)

```yaml
id: WCAP-<SCOPE>-<YYYY>-<NNN>   # stable forever; SCOPE = SYS, GLD, …
title: one sentence, the defect not the symptom
scope: {repo: …, tag: audit/<yyyy-mm>/<scope>, commit: …}
location:
  - {file: …, lines: [from, to]}    # at the audit tag
class: C6                          # taxonomy ID, §5
severity: medium                   # must equal MATRIX[impact][likelihood], §7
impact: medium                     # of the consequence, not of the condition
likelihood: medium                 # that the impact materialises, not that the condition exists
asset: …                           # from the threat model
invariant: I4                      # or "-"
status: open                       # open | fixed | mitigated | accepted | invalid
description: >
  what the code does, with the lines quoted
attack_scenario: >
  preconditions, actor, ordered steps, observable result; and what bounds the severity
proof:   {type: test | transaction-sequence | reasoning, ref: …}
recommendation: >
  the class fix, then the symptom fix
remediation:
  ticket: WBP-…
  pr: …
  regression_test: file::case — red on <commit> at <line>, green on the fix
  verified_by: who (a session that did not write the fix), by what protocol
  verified_at: YYYY-MM-DD
  verification: >
    the red line, the green binary, the class-versus-symptom reading, the verdict
  deployed: >
    tag, wasm hash, block, transaction, time; hash verified on chain
notes: >
  history, residuals, re-scopings, dated
```

`render.py --summary` validates the matrix and exits non-zero on a mismatch, so no rendering
can carry a severity the evidence does not support.

## 7. Severity matrix

Impact × likelihood, kept comparable with third-party reports.

| | Likelihood: High | Medium | Low |
|---|---|---|---|
| **Impact: Critical** (chain halt, unbounded mint, treasury drain, authority takeover) | Critical | Critical | High |
| **Impact: High** (bounded fund loss, schedule manipulation, permanent DoS of an action) | Critical | High | Medium |
| **Impact: Medium** (griefing, temporary DoS, incorrect accounting) | High | Medium | Low |
| **Impact: Low** (dead code, misleading errors, doc drift) | Medium | Low | Info |

Critical/High block a release. Medium needs a ticket with an owner before release. Low/Info are
logged and batched. Severity is judged from the code and the chain state that the code
reads; operational facts that are not properties of the code are recorded as context, not as
severity inputs.

---

## 8. Scorecard

Six dimensions, weighted for what an exchange integration depends on: that the deployed code
is the reviewed code, that funds cannot move without authorisation, and that upgrades are
controlled. Weights are fixed across revisions.

| Dimension | Weight | What it measures |
|---|---|---|
| Security | 35% | the register: what was found, what is fixed and verified, what is open, and why the score is not higher |
| Supply chain & reproducibility | 15% | every deployed contract reproduced from a named source and toolchain; deploys verified by hash |
| Governance & upgrade safety | 15% | upgrade path tooled and exercised; privileged setters bounded; allow-lists equal to live code; the custody the code depends on |
| Test coverage | 15% | cases, actions referenced, guard branches asserted, invariants tested, cost measured |
| Code quality | 10% | defect classes closed as process (ratchets), residuals stated |
| Documentation | 10% | security policy, provenance, deploy runbooks, architecture of the project-specific subsystems |

Scores are read on this scale, and each dimension's basis names what holds it:

| Band | Meaning |
|---|---|
| 9.0–10 | No material deficiency; any residual is stated, bounded and outside the reviewed code's control |
| 8.0–8.9 | Deficiencies found were fixed, deployed and independently verified; what remains is hygiene or a design choice deferred with reasons |
| 7.0–7.9 | At least one material item open or unverified, or a structural gap that limits what can be claimed |
| 5.0–6.9 | Open findings that bear on funds, consensus membership or custody, or a surface not reviewed |
| below 5 | Unreviewed, not reproducible, or an open High |

The overall score is the weighted sum, rounded to one decimal. Every revision states, per
dimension, the delta and what changed; a score never moves for merged-but-undeployed code.

## 9. Report conventions

- **Retractions and corrections** are a standing section. A claim that was wrong is corrected
  in place *and* listed there with the date.
- **Dismissed with reasoning** is a standing section: every candidate that looked like a bug
  and was not, with the reason.
- **Coverage** lists every file with lines, origin and status, then the sweep and test figures.
- The register marks each finding "✔ verified" only from `remediation.verified_by`, and
  "deployed" only from `remediation.deployed`.
- Findings whose subject is key custody or repository process (class H) are reported under
  their own heading so a reader of the code assessment can separate them from code findings;
  an external edition may move them to an appendix, and says so in its scope line.
- A public architecture overview of the project-specific subsystems (the audit's threat model
  restated as documentation, with each invariant's pinning test named) is part of the
  documentation dimension and is expected to exist in `docs/`.

## 10. Running it

```bash
# Phase 0
git tag audit/<yyyy-mm>/<scope> <commit>
docker run --rm [--cgroup-parent … --cpus N] -v "$PWD":/opt/contracts -w /opt/contracts <image> \
  bash -c "make build && make -jN -C build"
.audit/verify-hashes.sh build                      # every account MATCH, or reproduce-deployed.sh

# Phase 2
python3 .audit/rules/wcap-check.py contracts --baseline .audit/rules/baseline.txt   # 0 new
python3 .audit/rules/test_wcap_check.py                                              # OK
python3 .audit/rules/test-coverage.py --list

# Phase 4 / 6 (inside the image)
./build/tests/unit_test --run_test=<suite>/<case>   # and the full suite as the merge gate
# pre-fix red: swap the pre-fix wasm into build/contracts/<c>/ and re-run the case

# Phase 5 (private repo)
python3 .audit/render.py --summary                  # exit 0
python3 .audit/render.py --report-tables .audit/report-src/generated   # register, verification, counts
python3 .audit/report-src/build-report.py .audit/report-src/final-report-v<N>.md  # expands includes
python3 .audit/report-src/md2html.py <in.md> <out.html>                            # Confluence body
python3 .audit/render.py --report-data > <private>/report-data.json
python3 .audit/report/build-pdf.py <private>/report-data.json <private>/report.pdf  # --meta for scores
```

Publishing: Confluence pages are updated with `format: html` and a fresh snapshot token, a
version message naming the ticket, and the revision history bumped; the PDF is attached to
the report page and to the delivery ticket; a public PR keeps `.audit/report/report-meta.yaml`
in step with the scorecard.
